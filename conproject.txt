3.3 หน้าที่ของ Folder/ไฟล์สำคัญ (สรุป)
    - routes = ชั้นรับ request + เลือก middleware (verifytoken, upload, validate, rateLimit)
    - controllers = ชั้น business logic คุยกับ Prisma โดยตรง (ไม่มี service layer)
    - middleware = auth (verifytoken) และ file upload (multer)
    - utils = validation (yup), error helper, rate limit
    - prisma = schema + migration + seed (ข้อมูลจังหวัด/อำเภอ/ตำบล)
    - socket = realtime แชท (ปัจจุบัน server แค่ broadcast ต่อ ไม่บันทึก DB ในตัว socket)
    - Frontend components = แบ่งตามโดเมน (auth/service/Chat/techUser/map/area/view/admin)

3.4 จุดเริ่มต้นการทำงานของระบบ
    - Backend: Backend/server.js
        ลำดับ: import routes -> createServer(app) -> new Server(io, cors "*") ->
        chatSocket(io) -> cors/morgan/express.json -> static '/uploads' ->
        mount ทุก route ที่ '/api' -> error handler -> listen port 3000 (hardcode)
        [ตรวจสอบจาก Source Code]
    - Frontend: FrontEnd/src/main.jsx -> BrowserRouter -> App.jsx (Routes)
        หน้าแรก path "/" = Home  [ตรวจสอบจาก Source Code]
    - Database: ต้องรัน migration + npm run seed (ข้อมูลที่ตั้งจังหวัด) ก่อนใช้งานจริง
      [ตรวจสอบจาก Source Code]

4.2 รายชื่อตาราง (Model) และ Field สำคัญ  [ตรวจสอบจาก Source Code: prisma/schema.prisma]

    (1) users
        Users_Id   Int  PK autoincrement
        Email      String @unique
        Password   String (bcrypt hash)
        Role       Role  (enum)
        Status     Status @default(ACTIVE)
        Created_At DateTime @default(now())
        Updated_At DateTime @updatedAt
        ความสัมพันธ์: Profile (1:1), Services (1:N), CustomerOrders (1:N, relation
        "CustomerOrders"), TechnicianOrders (1:N, relation "TechnicianOrders"),
        Addresses (1:N), ServiceAreas (1:N)

    (2) profiles
        Profile_Id PK, Users_Id Int @unique (FK -> users), First_Name?, Last_Name?,
        Phone?, Avatar?, Gender? (enum), Birth_Date?, Created_At, Updated_At
        ความสัมพันธ์: users 1:1
        หมายเหตุ: ฟิลด์ Address ถูก "ลบออก" แล้วใน migration 20260823061739
        (ย้ายไปตาราง addresses) [ตรวจสอบจาก Source Code: migration]

    (3) addresses
        Address_Id PK, Users_Id FK, Address?, Province?, District?, Subdistrict?,
        Postal_Code?, Latitude Float (NOT NULL), Longitude Float (NOT NULL),
        Is_Default Boolean @default(false), Created_At, Updated_At

    (4) service_areas
        Area_Id PK, Users_Id FK, Province String, Created_At
        หมายเหตุ: แต่ละแถว = 1 จังหวัดที่ช่างรับงาน (ไม่มี unique constraint)
        ฟิลด์ District เคยมี แต่ถูก drop ใน migration 20260826131224

    (5) services
        Service_Id PK, Users_Id FK, Title String, Category ServiceCategory (enum),
        Description?, Price Float, Image?, Created_At, Updated_At
        ความสัมพันธ์: users (เจ้าของ/ช่าง), orders 1:N, chats 1:N

    (6) orders
        Order_Id PK, Users_Id FK (ลูกค้า), Tech_Id FK (ช่าง), Service_Id FK,
        Final_Price Float?, Work_Date DateTime?, Work_Date_End DateTime?,
        Status OrderStatus @default(ACCEPTED), Created_At, Updated_At
        ความสัมพันธ์: User (relation "CustomerOrders"), TechUser (relation
        "TechnicianOrders"), Service, Review (1:1 optional), BOQ (1:1 optional)

    (7) boqs
        BOQ_Id PK, Order_Id Int @unique (FK), Total_Amount Float @default(0),
        Created_At, Updated_At ; Items: boq_items 1:N

    (8) boq_items
        BOQ_Item_Id PK, BOQ_Id FK, Name, Description?, Quantity Float,
        Unit String, Unit_Price Float, Total_Price Float, Created_At, Updated_At

    (9) reviews
        Review_Id PK, Order_Id Int @unique (FK), Rating Int, Comment?, Created_At
        (ไม่มี Updated_At; ไม่มี FK ตรงไปยัง users/services ต้อง join ผ่าน orders)

    (10) chats
        Chat_Id PK, Service_Id FK, Room_Id String, Sender_Id Int, Receiver_Id Int,
        Type ChatType @default(MESSAGE), Message?, Price?, Work_Date?, Work_Date_End?,
        Image?, Created_At
        หมายเหตุ: Sender_Id / Receiver_Id เป็น Int ธรรมดา "ไม่มีความสัมพันธ์ (relation)"
        กับ users ใน Prisma

    (11) provinces
        Province_Id PK, Name @unique, Created_At, Updated_At ; Districts 1:N

    (12) districts
        District_Id PK, Province_Id FK, Name, Created_At, Updated_At ; Subdistricts 1:N

    (13) subdistricts
        Subdistrict_Id PK, District_Id FK, Name, Postal_Code?, Created_At, Updated_At

4.3 ความสัมพันธ์ระหว่างตาราง (สรุป)
    users 1--1 profiles
    users 1--N services           (users.Users_Id = services.Users_Id)
    users 1--N addresses
    users 1--N service_areas
    users 1--N orders (เป็นลูกค้า: orders.Users_Id)
    users 1--N orders (เป็นช่าง: orders.Tech_Id)
    services 1--N orders
    services 1--N chats
    orders 1--1 reviews (ผ่าน Order_Id @unique)
    orders 1--1 boqs    (ผ่าน Order_Id @unique)
    boqs   1--N boq_items
    provinces 1--N districts 1--N subdistricts
    หมายเหตุ: chats ไม่มี FK ไป users; addresses/service_areas เก็บชื่อจังหวัดเป็น string
    (ไม่ได้ FK ไป provinces) → ข้อมูลชื่อจังหวัดอาจไม่ตรงกับตาราง provinces

4.4 Enum และสถานะต่าง ๆ  [ตรวจสอบจาก Source Code]
    Role          : USER | TECHNICIAN | ADMIN
    Status        : ACTIVE | INACTIVE | BANNED
    Gender        : MALE | FEMALE | OTHER
    OrderStatus   : ACCEPTED | IN_PROGRESS | WAITING_CONFIRM | COMPLETED | CANCELLED
    ServiceCategory: ELECTRICAL | PLUMBING | AIR_CONDITIONER | PAINTING |
                     CONSTRUCTION | FURNITURE | CLEANING | OTHER
    ChatType      : MESSAGE | IMAGE | PRICE_OFFER | PRICE_ACCEPT | PRICE_REJECT

    สถานะ Order ที่โค้ดใช้จริง (ดูข้อ 7):
      ACCEPTED (ค่าเริ่มต้นตอนสร้าง order) -> IN_PROGRESS -> WAITING_CONFIRM -> COMPLETED
      CANCELLED มีใน enum แต่ backend "ไม่เคยตั้งค่า" (ดูข้อขัดแย้งในข้อ 10)

4.5 ข้อจำกัด/เงื่อนไขของฐานข้อมูล  [ตรวจสอบจาก Source Code]
    - Unique: users.Email, profiles.Users_Id, boqs.Order_Id, reviews.Order_Id,
      provinces.Name
    - 1 Order มีได้ 1 Review และ 1 BOQ เท่านั้น
    - FK ทั้งหมดเป็น ON DELETE RESTRICT / ON UPDATE CASCADE (ตาม migration.sql)

    - Rating เป็น Int แต่ "ไม่มี check 1-5" ทั้ง DB และ validation
    - Latitude/Longitude ใน addresses เป็น NOT NULL (frontend บังคับให้ปักหมุด)
    - ข้อมูลจังหวัด/อำเภอ/ตำบล มาจาก seed (prisma/data/*.json) ต้องรัน seed ก่อน
    - ยังไม่มีตาราง notifications / payments / audit logs / refresh tokens
    - ชื่อ Database/ผู้ใช้/รหัสผ่าน ตาม .env (root/1234) ใช้เฉพาะเครื่อง dev
      → production ต้องเปลี่ยน [ต้องยืนยัน]

6. System Workflow
--------------------------------------------------------------------------------
6.1 สมัครสมาชิก + เข้าสู่ระบบ  [ตรวจสอบจาก Source Code]
    1) ผู้ใช้กรอก Email/Password ที่ /register (yup ตรวจ email + password >= 6 +
       confirm password ตรงกัน)
    2) POST /api/register -> ตรวจ email ซ้ำ -> bcrypt hash (round 10) ->
       สร้าง users โดย Role="USER", Status="ACTIVE"
    3) frontend เรียก POST /api/login อัตโนมัติ -> เก็บ token + user ลง localStorage
       (key: "token", "user")
    4) แสดงฟอร์ม Newprofile (สร้าง profiles: ชื่อ/นามสกุล/เบอร์ 10 หลัก/เพศ/วันเกิด
       + อัปโหลดรูปผ่าน /api/uploadprofile)
    5) ทุก request ที่ต้องล็อกอินแนบ header authorization = <token> (ไม่ใส่ "Bearer")
    6) Logout = ลบ localStorage แล้วกลับหน้าแรก

6.2 ตั้งค่าข้อมูลช่าง (ก่อนรับงาน)  [ตรวจสอบจาก Source Code]
    1) เปลี่ยน Role เป็น TECHNICIAN (ต้องเรียก PATCH /api/updaterole — ยังไม่มี UI)
    2) เพิ่มพื้นที่ให้บริการ: /api/newservicearea (เลือกจังหวัดจาก /api/readprovinces)
    3) สร้างบริการ: /api/newservice (Title, Category, Description, Price, รูป)
    4) ข้อมูลจะแสดงในหน้าแรก (Home -> Show -> /api/listservice หรือ searchservices)

6.3 ค้นหาบริการ -> ติดต่อช่าง  [ตรวจสอบจาก Source Code]
    1) Home: พิมพ์คำค้น (Enter) หรือกดปุ่มหมวด (แมปไทย->enum) หรือดูทั้งหมด
    2) Show.jsx เรียก /api/searchservices?Category= / ?q= หรือ /api/listservice
    3) กรองจังหวัดฝั่ง client จาก User.ServiceAreas
    4) คลิกการ์ด -> modal แสดง ShowService (รายละเอียด, พื้นที่ให้บริการ, รีวิว)
    5) กด "ติดต่อผู้รับงาน" -> สร้าง Room_Id = `${Service_Id}_${minUserId}_${maxUserId}`
       แล้ว navigate ไป /chat พร้อม state (Room_Id, Service_Id, ผู้ส่ง, ผู้รับ,
       otherUserName, message = "สนใจงานบริการนี้ครับ")
    6) ChatContainer ส่งข้อความแรกอัตโนมัติ (POST /api/newmessage)

6.4 แชท + เสนอราคา + สร้าง Order  [ตรวจสอบจาก Source Code]
    1) ทั้งสองฝ่ายคุยกันในห้อง (ข้อความ/รูป) — realtime ด้วย socket event
       join_room + send_message + receive_message
    2) ฝั่งช่าง (ตรวจจาก serviceOwnerId == currentUserId) กด "เสนอราคา"
       -> POST /api/offer-price {Price, Work_Date, Work_Date_End, ...}
       -> chats.Type = PRICE_OFFER
    3) ฝั่งผู้ใช้เห็นข้อเสนอ กด "ยอมรับ"
       -> POST /api/createorder {Users_Id=Receiver, Tech_Id=Sender, Service_Id,
          Final_Price=Price, Work_Date, Work_Date_End, Chat_Id}
       -> backend เปลี่ยน chat เป็น PRICE_ACCEPT และสร้าง orders Status=ACCEPTED
       -> frontend emit send_message เพื่อให้อีกฝ่ายเห็นสถานะยอมรับ
    4) กด "ปฏิเสธ" -> PATCH /api/rejectPrice -> chats.Type = PRICE_REJECT

6.5 ดำเนินงาน -> ตรวจรับ -> (รีวิว)  [ตรวจสอบจาก Source Code]
    1) ช่างเห็นงานใน Profile > กำหนดการ > แท็บ "ช่าง" (GET /api/readtechorder/:id)
       กด "เริ่มงาน" -> PATCH /api/startorders/:id -> Status=IN_PROGRESS
    2) กด "เสร็จสิ้นงาน" -> PATCH /api/finishorders/:id -> Status=WAITING_CONFIRM
    3) ผู้ใช้เห็นในแท็บ "ผู้ใช้" (GET /api/readorderbyuserid/:id) เลือก
       "ยืนยัน" -> PATCH /api/confirmorders/:id -> Status=COMPLETED
       หรือ "ยกเลิก" -> PATCH /api/rejectorders/:id
       [ขัดแย้ง: frontend ส่ง Status="CANCELLED" แต่ backend ตั้งเป็น IN_PROGRESS]
    4) รายละเอียดงาน (DetailOrder/DetailOrderUser) แสดงข้อมูลงาน + โปรไฟล์อีกฝ่าย +
       ที่อยู่ + แผนที่ + ปุ่มดู BOQ
    5) รีวิว: API POST /api/createreview พร้อมเมื่อ Status=COMPLETED แต่ยังไม่มี
       หน้าจอให้ผู้ใช้เขียนรีวิว
    6) การชำระเงิน: ยังไม่มีขั้นตอนในระบบ (มีแค่หน้า QrTest ทดลอง)

6.6 BOQ  [ตรวจสอบจาก Source Code]
    1) ช่างเปิดห้องแชทของ Order ที่ Status=ACCEPTED (useMatchedOrder หา Order_Id)
    2) กด "สร้างรายการ" -> กรอกตาราง -> ยืนยัน -> POST /api/newboq
       (server คำนวณ Total_Price = Quantity * Unit_Price และ Total_Amount)
    3) ระบบส่งข้อความ "BOQ_CREATED:<Order_Id>" เข้าห้องแชท
    4) ปลายทางกด "ดูใบเสนอราคา" -> GET /api/readboqorder/:Order_Id ->
       navigate ไป /BOQPreview แสดง PDF (หรือดาวน์โหลด BOQ.pdf)

6.7 ขั้นตอนที่ยังไม่ครบใน workflow (ต้องยืนยันว่าต้องการแบบนี้หรือไม่)

    - การแจ้งเตือนเมื่อมีข้อเสนอ/งานใหม่
    - การเขียนรีวิว

    - การปิดงาน/สรุปยอดหลังชำระเงิน

7. Business Rules
--------------------------------------------------------------------------------
7.1 สิทธิ์ของ USER  [ตรวจสอบจาก Source Code]
    - สมัคร/เข้าสู่ระบบ, แก้ไขโปรไฟล์/ที่อยู่ของตัวเอง
    - ดูบริการทั้งหมด/ค้นหา, ดูโปรไฟล์ช่าง, ดูรีวิว
    - เปิดแชทกับเจ้าของบริการ, ยอมรับ/ปฏิเสธข้อเสนอราคา
    - ดูงานของตัวเอง (orders.Users_Id = id), ยืนยันงาน (WAITING_CONFIRM -> COMPLETED)
    - "ไม่สามารถ" สร้าง/แก้ไข/ลบบริการของคนอื่นได้ (controller เช็ค Users_Id)
    - ข้อจำกัดที่ควรมีแต่ยังไม่มี: USER สามารถเรียก API ของช่าง/แอดมินได้ถ้ามี token

7.2 สิทธิ์ของ TECHNICIAN  [ตรวจสอบจาก Source Code]
    - สร้าง/แก้ไข/ลบบริการของตัวเอง (ตรวจ Users_Id ใน body)
    - เพิ่ม/ลบพื้นที่ให้บริการของตัวเอง
    - เสนอราคาในแชท (frontend จำกัดปุ่มเฉพาะเจ้าของบริการ)
    - เริ่มงาน (ACCEPTED -> IN_PROGRESS) และแจ้งเสร็จ (-> WAITING_CONFIRM)
    - สร้าง BOQ ของ Order ที่ตัวเองเป็นช่าง (backend ไม่ได้ตรวจ Tech_Id)
    - ดูงานของตัวเอง (orders.Tech_Id = id)

7.3 สิทธิ์ของ ADMIN  [ตรวจสอบจาก Source Code + ต้องยืนยัน]
    - ตาม enum: มี role ADMIN
    - API ที่คาดว่าเป็นของ ADMIN: listuser, readuser, amountuser, updaterole,
      updatestatus, updateemail, updatepassword
    - ปัจจุบัน: ไม่มีการตรวจ role ในทุก endpoint ข้างต้น
    - สิทธิ์ที่ต้องการจริงของ ADMIN: [ต้องยืนยัน]

7.4 เงื่อนไขการสร้างข้อมูล  [ตรวจสอบจาก Source Code]
    - users: Email ห้ามซ้ำ, Password ขั้นต่ำ 6 ตัวอักษร (yup), Role บังคับเป็น USER
      ตอนสมัคร, Status เริ่มต้น ACTIVE
    - profiles: 1 user มีได้ 1 profile (Users_Id unique) สร้างซ้ำจะได้ 400
    - services: ต้องมี Users_Id ที่มีอยู่จริง, Title, Category, Price > 0
      (yup: positive), Description ไม่บังคับ
    - addresses: Province, Latitude, Longitude, Is_Default บังคับ (yup)
    - orders: ต้องมี Users_Id, Tech_Id, Service_Id, Final_Price, Work_Date,
      Work_Date_End (backend ไม่ validate แต่ frontend ส่งครบจากข้อเสนอราคา)
    - reviews: order ต้องมีจริง + Status=COMPLETED + ยังไม่มีรีวิวของ order นี้
    - boqs: order ต้องมีจริง + ยังไม่มี BOQ ของ order นี้
    - chats: ต้องมี Service_Id, Room_Id, Sender_Id, Receiver_Id
      Type ถูกกำหนดจาก "มีไฟล์แนบหรือไม่" (IMAGE/MESSAGE)

7.5 เงื่อนไขการแก้ไขและลบข้อมูล  [ตรวจสอบจาก Source Code]
    - services: แก้/ลบได้เฉพาะเจ้าของ (service.Users_Id === body.Users_Id) ไม่งั้น 403
      และเมื่อเปลี่ยนรูป/ลบ จะลบไฟล์เดิมใน uploads ด้วย
    - addresses: แก้/ลบได้เฉพาะเจ้าของ (body.Users_Id) ไม่งั้น 403
    - service_areas: update ตรวจ Area_Id + Users_Id (403 ถ้าไม่ตรง) แต่ delete
      "ไม่ตรวจเจ้าของ"
    - reviews: update/delete ไม่ตรวจเจ้าของหรือ role ใด ๆ
    - chats: ไม่มีการแก้ไข/ลบข้อความ
    - users: ไม่มีการลบบัญชี (ใช้ Status=BANNED/INACTIVE แทน)

7.6 เงื่อนไขการเปลี่ยนสถานะ  [ตรวจสอบจาก Source Code]
    - Order:
        ACCEPTED --startorders--> IN_PROGRESS
        IN_PROGRESS --finishorders--> WAITING_CONFIRM
        WAITING_CONFIRM --confirmorders--> COMPLETED
        rejectorders --> ตั้งเป็น IN_PROGRESS (ไม่ใช่ CANCELLED) [ขัดแย้ง]
      ไม่มีการตรวจสถานะก่อนเปลี่ยน (เรียกซ้ำ/ข้ามสถานะได้)
    - User Status: เปลี่ยนได้ผ่าน updatestatus (ACTIVE/INACTIVE/BANNED)
      และ login จะปฏิเสธถ้า Status != ACTIVE (403 "Account is not active")
    - Chat Type: MESSAGE/IMAGE ตอนสร้าง, PRICE_OFFER ตอนเสนอราคา,
      PRICE_ACCEPT ตอนสร้าง order, PRICE_REJECT ตอนปฏิเสธ

8.1 รูปแบบทั่วไป  [ตรวจสอบจาก Source Code]
    - Base URL: http://localhost:3000/api
    - Content-Type: application/json (ยกเว้นอัปโหลด = multipart/form-data, field "file")
    - Authentication: header "authorization: <JWT>" (ไม่มีคำว่า Bearer)
    - Response สำเร็จ: { "result": ... } หรือ { "message": "...", "result": ... }
    - Response ผิดพลาด: { "message": "..." } + HTTP status = err.code || 500
    - Static file: http://localhost:3000/uploads/<filename>
    - Error handler กลางอยู่ใน server.js (4 พารามิเตอร์)

8.3 Authentication Middleware  [ตรวจสอบจาก Source Code]
    - middleware/verifytoken.js: อ่าน req.headers["authorization"] ->
      ถ้าไม่มี token โยน error 401 "Please enter the token"
      -> jwt.verify(token, process.env.SECRET) -> ถ้าผิดโยน 403 "token invalided"
      -> สำเร็จเรียก next()
    - ข้อสังเกต: ไม่ได้เก็บ decoded user ลง req (เช่น req.user) ทำให้ controller
      ไม่รู้ว่าใครเรียก และไม่สามารถตรวจสิทธิ์จาก token ได้
    - ข้อสังเกต: createError ถูกเรียกใน callback ของ jwt.verify (กรณี token ผิด)
      ซึ่งเป็น async context → error อาจไม่ถูกส่งเข้า error handler ปกติ

8.4 Authorization
    - ไม่มี middleware ตรวจ Role
    - การตรวจสิทธิ์ระดับข้อมูลทำใน controller บางจุด (services, addresses,
      service_areas update) โดยเทียบ Users_Id จาก body กับเจ้าของข้อมูล
    - endpoint ที่ยังเปิดกว้าง (ไม่ต้อง token เลย): register, login, listservice,
      searchservices, readservice, readprofile, listuser, readuser, amountuser,
      order GET ทุกตัว, review ทุกตัว, chat rejectPrice, address ทุกตัว,
      location ทุกตัว, boq ทุกตัว, servicearea (สร้าง/ลบ/แก้)

8.5 Validation  [ตรวจสอบจาก Source Code]
    - ใช้ yup ผ่าน utils/validate.js: registerscheema, loginscheema,
      updateemailcheema, createServiceSchema, addressSchema
    - validate() ใช้ abortEarly:false แล้วรวม error ด้วย "," ส่งเป็น Error ธรรมดา
    - endpoint อื่น (order, chat, review, boq, profile, role/status) ไม่มี schema
      → พึ่งการแปลง Number() ใน controller และ Prisma error

8.6 Error Handling  [ตรวจสอบจาก Source Code]
    - createError(code, msg) => throw Error พร้อม .code
    - server.js: app.use((err,req,res,next) => res.status(err.code||500)
      .json({message: err.message||"server error"}))
    - ข้อสังเกต: หลายจุดเรียก createError โดยไม่ใส่ "throw"/"return"
      (เช่น auth.controller, profile.controller) → error ถูกสร้างแต่ไม่ถูกโยน
      ทำให้บางเคสตอบ 200 พร้อมข้อมูลผิด หรือไปพังที่ขั้นตอนถัดไป
    - Prisma error (เช่น unique constraint) จะกลายเป็น 500 พร้อมข้อความดิบ

8.7 การเชื่อมต่อ Frontend กับ Backend  [ตรวจสอบจาก Source Code]
    - axios เรียก URL เต็ม http://localhost:3000/api/... กระจายในทุกคอมโพเนนต์
    - token อ่านจาก localStorage.getItem("token") ใส่ header authorization
    - ข้อมูลผู้ใช้ปัจจุบันอ่านจาก localStorage.getItem("user") -> .payload.id / .role
    - ไม่มี Axios instance กลาง / ไม่มี interceptor / ไม่มี .env ของ frontend
    - รูปภาพใช้ http://localhost:3000/uploads/<filename>
    - Socket ใช้ io("http://localhost:3000") (hardcode ใน useSocket.js)

9.1 Socket.IO Architecture  [ตรวจสอบจาก Source Code]
    - Server: Backend/socket/chat.socket.js ถูกเรียกจาก server.js (chatSocket(io))
    - CORS: origin "*"
    - ไม่มี authentication ใน socket (ไม่ตรวจ token ตอน connect)
    - Client: hooks/useSocket.js -> io("http://localhost:3000"), คืน socket instance

9.2 Chat Room และ Event  [ตรวจสอบจาก Source Code]
    - Room_Id format: `${Service_Id}_${minUserId}_${maxUserId}` (utils/generateRoomId.js)
      → 1 บริการ + 1 คู่สนทนา = 1 ห้อง (ห้องถูกสร้างโดยปริยายเมื่อมีข้อความแรก)
    - Event ฝั่ง client -> server:
        "join_room"     payload: roomId (string) -> socket.join(roomId)
        "send_message"  payload: chat object (result จาก API) -> server emit ต่อ
    - Event ฝั่ง server -> client:
        "receive_message" payload: chat object (ใช้ทั้งข้อความใหม่และอัปเดตสถานะ
                          PRICE_ACCEPT/PRICE_REJECT)
    - "disconnect" -> log "User Disconnected"
    - การบันทึก DB เกิดจาก REST API (/newmessage, /offer-price, /rejectPrice)
      แล้ว client ค่อย emit ข้อมูลลงห้อง (ไม่ได้บันทึกใน socket handler)

9.3 การส่งข้อความและรูปภาพ  [ตรวจสอบจาก Source Code]
    - ข้อความ: POST /api/newmessage (multipart) -> Type = MESSAGE (ถ้าไม่มีไฟล์)
    - รูป: แนบ field "file" -> Type = IMAGE, เก็บชื่อไฟล์ใน chats.Image
      แสดงผลด้วย <img src="http://localhost:3000/uploads/<Image>">
    - ฝั่ง client ทำ optimistic UI ด้วย Chat_Id ชั่วคราว (crypto.randomUUID())
      แล้วแทนที่ด้วยข้อมูลจริงจาก API
    - ไม่มี limit ขนาดไฟล์/ชนิดไฟล์ใน multer (รับทุกไฟล์)

9.4 Map และ Geocoding  [ตรวจสอบจาก Source Code]

    - พิกัดได้จาก: (ก) navigator.geolocation (ข) คลิกบนแผนที่
